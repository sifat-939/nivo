## ১. এক ইনভয়েসে অতিরিক্ত টাকা বরাদ্দ

**উদাহরণ:** দুটি ইনভয়েসে বকেয়া ১০০ ও ২৫০। মোট ৩৫০ পেমেন্ট প্রথম ইনভয়েসে ৩৫০ এবং দ্বিতীয়টিতে ০ বরাদ্দ করলে aggregate validation পাস করে। Outstanding update চালালে প্রথমটির বকেয়া −২৫০, দ্বিতীয়টির ২৫০ থাকে।

**কারণ:** `Payment.validateReferenceOutstanding()` শুধু মোট বকেয়ার সঙ্গে মোট পেমেন্ট মেলায়। প্রতি reference row-এর amount তার নিজস্ব invoice outstanding ছাড়াচ্ছে কি না পরীক্ষা করে না। এরপর `updateReferenceDocOutstanding()` প্রতিটি row আলাদাভাবে বাদ দেয়।

**সূত্র:** [Payment.ts:415](../models/baseModels/Payment/Payment.ts#L415), [Payment.ts:456](../models/baseModels/Payment/Payment.ts#L456); child model-এও amount-এর এমন validation নেই।

**যাচাই:** `:memory:`-তে দুটি submitted invoice, বাস্তব validators এবং outstanding-update method দিয়ে ৩টি assertion। সম্পূর্ণ UI থেকে payment submit করার end-to-end পরীক্ষা নয়। [পুনরুৎপাদনের স্ক্রিপ্ট](audit/repro-payment-allocation.ts)।

**ঠিক করার দিক:** প্রতিটি invoice-এর মোট বরাদ্দ যাচাই করতে হবে; একই invoice একাধিক row-তে থাকলেও যোগফল তার বকেয়া ছাড়াতে পারবে না। প্রত্যাখ্যাত পেমেন্টে কোনো balance/ledger পরিবর্তন হবে না—এমন regression test দরকার।

## ২. রিটার্নের পেমেন্ট বাতিলের হিসাব উল্টো

**উদাহরণ:** রিটার্ন ইনভয়েসের বকেয়া ১০০, refund/payment ৪০। Submit-এর পরে ৬০। Cancel করলে ১০০ হওয়ার বদলে ২০ হয়।

**কারণ:** return branch-এ submit allocation বাদ দেয়; `_revertReferenceOutstanding()`-ও বাদ দেয়। Cancellation-এ আগের পরিমাণ ফিরিয়ে যোগ করা উচিত। Return invoice-এর outstanding সূত্রটি ধনাত্মক মান ফেরত দেয়।

**সূত্র:** [Payment.ts:468](../models/baseModels/Payment/Payment.ts#L468), [Payment.ts:519](../models/baseModels/Payment/Payment.ts#L519), [Invoice.ts:1217](../models/baseModels/Invoice/Invoice.ts#L1217)।

**যাচাই:** আসল দুটি Payment method ও Money arithmetic, কিন্তু reference lookup/save-এর জায়গায় isolated stub ব্যবহার করে ১০০ → ৬০ → ২০ দেখা গেছে। পূর্ণ return ledger lifecycle পরীক্ষা হয়নি। [স্ক্রিপ্ট](audit/repro-return-cancel.ts)।

**ঠিক করার দিক:** submit-এর বিপরীত অপারেশন প্রয়োগ করতে হবে। Sales return এবং purchase return-এর partial/full payment ও cancel-এ invoice/party/ledger একসঙ্গে পরীক্ষা করতে হবে।

## ৩. Migration backup-এর নামের সংঘর্ষ

**ঘটনা:** একই ডাটাবেস, stored version এবং UTC দিনে backup আবার তৈরি হলে আগের ফাইলের নামই ব্যবহৃত হয়। Migration/patch আংশিক ব্যর্থ হওয়ার পরে retry করলে নতুন backup আগের recovery copy প্রতিস্থাপন করতে পারে।

**সূত্র:** [manager.ts:182](../backend/database/manager.ts#L182), [manager.ts:203](../backend/database/manager.ts#L203), migration-এর আগে backup call [manager.ts:75](../backend/database/manager.ts#L75)।

**যাচাই:** অস্থায়ী SQLite DB-তে একই destination-এ দুবার backup করে প্রথম snapshot বদলে যাওয়ার বিষয়টি চালিয়ে নিশ্চিত করা হয়েছে। ইচ্ছাকৃতভাবে কোনো বাস্তব migration ব্যর্থ করা হয়নি। [স্ক্রিপ্ট](audit/repro-backup-collision.cjs)।

**ঠিক করার দিক:** timestamp ও unique suffix দিয়ে আলাদা backup তৈরি; বিদ্যমান recovery copy কখনও নীরবে overwrite না করা। Installer-এর নিজস্ব microsecond timestamp backup আলাদা ব্যবস্থা; এই বাগটি অ্যাপের migration backup-এ।

## ৪. POS closing-এর ঋণাত্মক অঙ্ক আটকে যায় না

**ঘটনা:** closing amount-এ ঋণাত্মক মান দিলে `validateClosingAmounts()` error তৈরি করেও নিজের empty catch-এ গিলে ফেলে। Caller এরপর closing date, opening shift ও shift document save করার দিকে এগোয়। পরের cash journal-এর অন্য validation এটিকে আটকাবে কি না, তা এখানে পরীক্ষিত নয়; তাই সম্পূর্ণ cash posting সফল হয়—এ দাবি করা হচ্ছে না।

**সূত্র:** [pos.ts:201](../src/utils/pos.ts#L201), [ClosePOSShiftModal.vue:222](../src/pages/POS/ClosePOSShiftModal.vue#L222), [ClosingAmounts schema](../schemas/app/inventory/Point%20of%20Sale/ClosingAmounts.json)।

**ঠিক করার দিক:** error caller পর্যন্ত পৌঁছাতে হবে; model স্তরেও nonnegative validation থাকতে হবে। Invalid input-এ shift বা journal-এর কোনো আংশিক পরিবর্তন যেন save না হয় তা পরীক্ষা করতে হবে।

## ৫. অফলাইনে POS শিফট বন্ধ হয় না

**ঘটনা:** `navigator.onLine` false হলে close flow সঙ্গে সঙ্গে `Device is offline` error দেয়। ফলে স্থানীয় POSClosingShift save ও cash transfer-এর আগেই কাজ থামে। ইন্টারনেট ছাড়া হিসাব চালানোর লক্ষ্য অনুযায়ী এটি কার্যকরী সীমাবদ্ধতা।

**সূত্র:** computed `isOnline` [ClosePOSShiftModal.vue:107](../src/pages/POS/ClosePOSShiftModal.vue#L107), বাধা [ClosePOSShiftModal.vue:216](../src/pages/POS/ClosePOSShiftModal.vue#L216)।

**যাচাই:** source branch থেকে নিশ্চিত; OS network বন্ধ করে পূর্ণ শিফট পরীক্ষা হয়নি।

**ঠিক করার দিক:** স্থানীয় shift close ও journal posting অফলাইনে চলবে; বাহ্যিক sync থাকলে সেটি আলাদাভাবে queue/retry হবে। পরিবর্তনের পরে offline open/sell/pay/close এবং পরে sync-এর end-to-end পরীক্ষা প্রয়োজন।

## ৬. টেমপ্লেট প্রিভিউয়ের একই পপআপ দুবার

**ঘটনা:** Shipment-এর মতো entry-শূন্য document type-এর template প্রথমবার খুললে একই `No Display Entries Found` সতর্কবার্তা দুবার দেখা যায়।

**কারণ:** component-টি keep-alive-এর ভেতরে থাকে; initial mount-এ `mounted()` ও `activated()` দুটো hook-ই `initialize()` চালায়। উভয়টি `setDisplayInitialDoc()`-এর একই warning খুলতে পারে।

**সূত্র:** [TemplateBuilder.vue:492](../src/pages/TemplateBuilder/TemplateBuilder.vue#L492), [TemplateBuilder.vue:499](../src/pages/TemplateBuilder/TemplateBuilder.vue#L499), [TemplateBuilder.vue:667](../src/pages/TemplateBuilder/TemplateBuilder.vue#L667), [Desk.vue:32](../src/pages/Desk.vue#L32)।

**ঠিক করার দিক:** initial initialization একবার করা বা concurrent call guard; reactivation-এ প্রয়োজনীয় refresh আলাদা করা। Empty ও non-empty document type-এ একবার warning/একবার initialization যাচাই করতে হবে। অ্যাপ বন্ধ হওয়ার সময় unsaved prompt-এর আলাদা বাগ নিশ্চিত হয়নি, তাই তালিকায় যোগ করা হয়নি।

## এই কাজের সঙ্গে ইতিমধ্যে ঠিক করা সমস্যা

`build/scripts/build.mjs`-এর URL rewrite সব ফাইলকে UTF-8 text হিসেবে লিখত; বড় PNG এবং WOFF2 font এতে নষ্ট হচ্ছিল। এখন শুধু text asset rewrite হয়; logic [assetPaths.mjs](../build/scripts/assetPaths.mjs)-এ আছে। PNG/font MIME type-ও নিবন্ধিত হয়েছে।

যাচাই: regression test পাস; packaged PNG ও Inter font-এর bytes মূলের সঙ্গে সমান; AppImage welcome, light/dark dashboard এবং ইনস্টল করা অ্যাপে logo image load যাচাই হয়েছে।
